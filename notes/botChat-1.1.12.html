botChat 1.1.12

本次更新主线是「跨会话记忆从空壳变成两个能用的文件」：仓库里并存的两套互相矛盾、也都从未通电的旧记忆实现整体移除，改为「两个 Markdown 文件 + 三个生效点」；副列区同时收敛为「一页恒一列」。

新增

  • 跨会话记忆落为两个 Markdown 文件：用户级 ~/.botchat/memory/USER.md（缺省上限 1,375 字符）与项目级 <工作区>/.botchat/memory/MEMORY.md（缺省上限 2,200 字符）。真相源是磁盘而不是数据库——可以直接用编辑器改、可以 git diff、可以放进版本库；没有向量库、没有 embedding、不按轮召回。条目之间用独占一行的 § 分隔。
  • 记忆注入块：会话上下文里出现 [MemoryDoc] 块，块头带文件路径与两级使用率（形如 user [3% — 44/1375 chars] | memory [2% — 56/2200 chars]），条目按级分节排在其后。两级都为空时整体不注入，不留空壳；超出预算时截断并显式写明「原文 N 字符、仅注入前 M 字符、全文在哪」，不静默截断。
  • memory 写入工具（仅主 Agent 可见）：三个动作 add / patch / remove——没有 read（内容已在上下文里）、没有 replace（整条覆盖会连带抹掉同一多事实条目里的其它事实）。patch / remove 用短唯一子串定位，命中数不为 1 就直接报错并回当前条目，不猜。现场合成的子 Agent 看不到该工具，连工具名都不可见。
  • 写入有门：超限报错逼腾位：容量按字符计（不折 token 估算），超限不静默截断，返回可决策的错误体——带 current_entries（现有全部条目）、usage（如 2100/2200）与 required_free（还需腾出多少字符）；add 可带 replacing_text，一次原子完成「移除 + 新增」。
  • 收尾自动归档：每轮结束时后台抽取一条候选（outcome / failure / lesson），过质量门后直接调用存储层写入，不经模型调工具——因此不会出现「回复里写了『已加入记忆』但其实没存」。只归档主 Agent 的收尾轮，同一会话同一时刻最多一个归档任务；容量不足时放弃该候选，不删既有条目腾位。
  • POST /api/memory/refresh 显式刷新：重读磁盘并冻结成新快照，响应里如实给出两级使用率与是否真的重建。一次刷新同时更新 [MemoryDoc] 与 [ProjectDoc]（AGENTS.md），避免出现「记忆是新的、协作规范还是上一版」。

改进

  • 记忆生效点只有三处：新会话、压缩锚点之后（当前未启用）、显式刷新。写入立即落盘，但不改变本轮已经发出的 prompt——改完文件发现不生效，先确认是否到了生效点，这是设计选择而非 bug。记忆块内不含时间戳、轮次号、run_id 等逐轮变量，跨轮逐字节稳定，不影响前缀缓存。
  • 落盘前的安全扫描：记忆会进 system prompt 且跨会话持久，落盘前扫三类红线——prompt 注入模式、凭据外泄模式、不可见/双向控制字符；命中即拒收并回报命中类别。只扫本次新增或修改的内容，不重扫既有条目，否则一个被手写投毒的文件连 remove 都写不进去，自救路径会自己堵死。
  • 副列区一页恒一列：此前副列区宽过约 609pt 就会并排显示两列，现在恒定一列，多出来的副面板走既有分页（页点条 / 横滑）访问，不再需要同时读两处。列组与布局预设不受影响（结构层仍允许多列共存，只是同一屏只显示一个），同一组的多列可被分页拆开。

修复

  • 跨会话记忆此前从未通电：旧实现里 memory_entry 表零读写调用方、/api/memory 的四个端点落在进程内字典（重启即空）、客户端等的 memory_update 事件两端都不存在、客户端记忆面板也没有装配点——链路整体悬空，同时又并存着两条方向相反的废弃路线（bash MCP 自管 / 每轮召回），谁也裁决不了。本轮清掉旧地基按上述模型重建。
  • 按会话清理记忆的死分支：memory_entry 没有 conversation_id 列，按会话级联清理记忆的分支一直抛 AttributeError 并被 except Exception: pass 静默吞掉。表已删除（迁移 j3c4d5e6f7a8），该分支与模型一并移除。

移除

  • 旧记忆体系的 REST 面：GET /api/memory、POST /api/memory/recall、POST /api/memory、GET /api/memory/namespaces 四个端点全部删除，不留兼容门面；记忆的读写改为「直接编辑两个 Markdown 文件 + memory 工具」，REST 面只保留「改完的文件生效」这一个动作。
  • 客户端记忆面板与其依赖（MemoryPanelView / MemoryService / LocalMemoryService / MemoryEntry 及本地 SwiftData 镜像容器）一并移除——这套 UI 此前没有装配点，用户侧无可见入口，记忆内容请用文件浏览/预览面板直接看磁盘上的两个 Markdown。
  • memory_entry 表的移除随服务端启动时自动执行的数据库迁移完成，无需手工操作（自建部署且设了 SKIP_MIGRATIONS=1 的环境需自行执行 alembic upgrade head）。
  • memory 工具属常驻 core 层，TOOL_CATALOG_CORE_LIMIT 缺省值由 12 抬到 13——否则它会按声明序被静默截断（实测被丢弃的正是 memory）。关闭 MEMORY_ENABLED 时该工具不出现在任何工具清单中，且零读盘、零注入。
